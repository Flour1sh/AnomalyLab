- **目标**：UE 5.8、Win64 Development、单人可玩版本

## 0. 产品目标、核心体验与完成条件

### 0.1 从 v0.4 到 v0.5 的体验变化

**旧流程（逻辑概括）**：主菜单 → 同一实验室地图入口处整备/购买 → A/B/C 箱子探索 → 回入口兑现/死亡 → 下一局。

**新流程（必须达到）**：

```text
L_MainMenu（沿用现有菜单，实际名称先审计）
    │ 新游戏 / 继续游戏
    ▼
L_Hub（新增：安全基地、出生/死亡后重生、商店、整备）
    ├─ 商店：跨局货币 / 扫描模块 / 装备 / 补给
    ├─ 终端：查看上一局报告 / 进入探索
    └─ 出发门 / 电梯：确认 Loadout → Loading → L_Lab
                                            │
                         L_Lab（探索独立 Level）
                         ├─ 动态箱位与局内状态
                         ├─ A/B/C 区域玩法 + 环境事件
                         ├─ 扫描、选择箱子、战利品和异常
                         └─ 撤离交互 / 死亡 / 技术异常
                                            │
                                            ▼
                              统一结算与存档（一次）
                                            │
                                  Loading → L_Hub
                                            │
                         出生于 Hub / 展示结果 / 可再购买
```

**关键体验**：Hub 永远是明确的非战斗安全空间；Lab 才能触发开箱、威胁和死亡。成功撤离回 Hub，死亡也回 Hub（本局未带出的物品丢失，已持有永久资产按 v0.4 规则保存）。下一次进入 Lab 是**新的一局**，不能继承上一局的怪物、开放箱、掉落或计时器。

### 0.2 DoD（Definition of Done）

1. **两个真实独立的 `.umap` Level**：`L_Hub` 与 `L_Lab`（可在审计后改名）；不是用一个地图内两个相隔很远的房间伪装关卡。
2. 从菜单进入 Hub，在 Hub 完成购买与装备整备，交互触发加载 Lab；成功、死亡、技术异常都经明确的结果流程返回 Hub；独立包真实输入连续完成 **至少 3 次往返**不崩溃、不重复结算。
3. v0.4 的商店/货币/SaveGame/升级效果与 v0.3 的扫描、箱选、背包、撤离和观察者/追逐者均在新地图流程正确工作；升级能在本次进入 Lab 时应用。
4. Hub/Lab 之间跨 Level 的状态转移**有可审计的状态归属、幂等与恢复机制**；不使用关卡 Actor 指针作为跨 Level 持久数据。
5. Lab 至少具有**有限随机的箱位与环境状态**：每轮仍保持 **A/B/C 各一候选、选一锁其他**的现有核心契约，随机从该区多个合法点中生成；相同种子复现。
6. 实装 **至少 2 个环境交互**（优先 B 配电、C 收容舱）和 **至少 2 个非纯掉落的动态事件**；提供明确反馈与对策，不能仅为随机播音效。
7. 保持低模实验室美术基调，有清晰的 Hub/Lab 视觉差异、加载遮挡与玩家引导；不用制作大规模新场景。
8. 720p/1080p 可见画面、完整 Win64 Development 包、可重建资产/场景脚本、旧版回归、新增跨关卡测试、恢复归档和人工测试单齐全。

### 0.3 本版明确不做

- 不做多人同步、在线持久化、完全程序化生成任意拓扑、复杂战斗系统、枪械伤害树、可破坏地图、无缝开放世界、正式 Shipping 发行。
- 不将 Hub 做成多人大厅；不实现自由回退到 Hub 来逃避结算；不强行增加新怪物种类。现有两种异常先接入动态事件。
- 不同时重写回合状态机、商店、SaveGame 和全部关卡。必要迁移须先提出最小改动方案。

## 1. 首要架构决策：两 Level 与状态生命周期

### 1.1 Level 划分与地图设计（P0，不得跳过）

**Hub 安全基地**：独立地图，第一版建议室内约 **16 × 20 m**（建议数值，允许按现有模型调整），入口出生点、整备/商店终端、出发闸门或电梯、上一局战报面板、少量陈设。不得生成危险箱、怪物、可结算 Loot；Hub 内无局内 HP 伤害、扫描扣费或计时。初次启动、撤离成功、死亡后均在 Hub 出生/复活。

```text
              [基地标识 / 简短指南]
                      │
 [商店终端] ── [整备区 / 出生点] ── [战报终端]
                      │
           [装备确认 / 出发电梯]
                      │
             Load → L_Lab
```

**Lab 探索实验室**：将现有 `L_Prototype` 的探索布局/材质/内容**复制/迁移**到 `L_Lab`，保留入口与走廊、A/B/C 区；移除在 Lab 内直接购买/复活的职责。原入口改成**撤离气闸/出口终端**，只能在合法返程阶段 E 撤离，禁止在那里直接购买永久装备。保留原场景可复建脚本，修改生成目标地图时必须有版本参数或独立脚本；不可误覆盖 Legacy 地图与归档。

```text
                  [撤离气闸/局内起点]
                            │
           [A 分析区] ─ [中央走廊] ─ [B 动力区]
                            │
                       [C 收容区]
```

**设计取舍**：先稳定“两地图切换”，再实现地图动态化。此版本保留 A/B/C 区域总体拓扑，不做全随机迷宫；随机的是每区候选箱位置、活动设备及事件组合。可选新捷径先只作为灰盒评估，不列为强制交付。

### 1.2 推荐 UE 生命周期归属（非实际现有类名）

| 数据/职责 | 推荐归属 | 生命周期 | 关键约束 |
|---|---|---|---|
| 永久货币、装备升级、已解锁项目 | `SaveGame` + 现有经济权威服务 | 跨启动 | 保持旧存档可读或定义明确迁移；绝不因关卡载入重置 |
| 本次 Hub→Lab 出发参数（购买后的装备、选定种子） | `GameInstance` 中 `RunTransitionContext` 或现有等价持久层 | 跨 `OpenLevel`，单次过渡 | 仅复制 ID/值，不存 UWorld Actor 指针；消耗标记/过渡序号 |
| 本局 HP、箱、扫描次数、背包、AI、事件状态 | Lab 的 GameMode/Subsystem/Actor（按已有实现） | 单局/单 Level | 每次进 Lab 初始化；回 Hub 必清理 |
| 结算快照与状态（成功/死亡/异常） | 独立结果 DTO + 唯一 RunId | 结算至 Hub 展示 | 最多结算一次；可查来源与时间；避免重复保存 |
| Hub UI、商店摆件、出生点 | Hub 自己的 Actor/Widget | Hub Level | 不依赖 Lab 场景 Actor |
| 菜单/加载界面 | UI/加载管理 | 全流程 | 不参与金币及胜负权威逻辑 |

推荐 `OpenLevel` 做最小可用的独立关卡切换；若既有工程已有 `GameInstance`、Subsystem、Async Load 或传送框架优先复用。**不要将 World Partition、Level Streaming 或 Seamless Travel 引为交付前提**。异步/加载画面可以作为独立小步骤，核心先保证正确。

### 1.3 必须实现的跨 Level 协议

```text
HubReady → Preparing → LaunchRequested → LoadingLab
→ LabInitializing → InRun → ExtractionRequested / Died / Error
→ FinalizingRun → ResultCommitted → LoadingHub → HubReady
```

- **权威触发**：出发/撤离/死亡均只能由合法阶段进入；重复按 E、关卡切换期间再按键、旧回调不得触发第二次 `OpenLevel` / 第二次结算。
- **RunId**：每局一个唯一且可追踪标识；一次结算事务按 RunId 去重。先产生不可变结算 DTO，再安全更新 SaveGame，再切回 Hub。
- **货币边界**：Lab 中拾取或展示的战利品不等于永久货币；仅合法成功撤离兑现；死亡清空局内携带物，永久账户不应倒退（除非已有合理既定消耗规则）。
- **库存边界**：永久装备与购买记录由持久层保存；Lab 本局拾取物只在本局有效；返回 Hub 时只保存依法兑现的收益。
- **异常边界**：玩家死亡与 E 撤离同帧冲突以死亡优先；技术异常不可自动发奖。离开过程中停止计时器、追逐及交互，防止异步回调访问旧世界。
- **重启恢复**：若游戏在 Lab 退出/崩溃，默认 **回 Hub 并视为未撤离，不奖励未兑现 Loot**；如旧 SaveGame 已支持断点恢复，先审计、记录迁移决定。不要在启动时把最后一次结果再次记账。
- **全路径回归**：主菜单进入 Hub、新建/读取档、Hub 购买→Lab 生效、撤离成功、死亡、重复结算、断电退出/重启、第二次出发等。

## 4. T34 — 地图重构：Hub + Lab（重点）

### 4.1 Hub 必须有的空间与操作

- `PlayerStart_Hub`：启动/复活稳定出生点；不要把死亡后的“复活”写成在 Lab 原地复活。
- `ShopTerminal`：触发 v0.4 既有商店 UI 和购买方法；无新经济系统。
- `LoadoutStation`：展示扫描/装备/消耗品与装备效果；能确认出发携带（按已有规则；如当前没有槽位切换，不擅自新增复杂装备栏）。
- `MissionTerminal` / `DepartureDoor`：显示关卡名称、预计风险、装备概览，按 E 确认出发。
- `RunReport`：返回后展示上一局收入、收容、死亡原因、耗时；仅展示结算快照，不在 UI 再调用入账函数。
- 视觉要求：安全照明、旧绿/铁灰/警示黄延续，搭配暖色整备区和明显的出发门；为 720p/1080p 中文提示留空间。

### 4.2 Lab 必须保留的系统

- 现有 A/B/C 区域功能性差异、扫描资源、奖励权重、拾取/背包、追逐者和观察者、终局状态机；旧装饰资产尽量复用。
- `PlayerStart_Lab` 位于原入口的气闸内；新 `ExtractionTerminal` 保持“玩家返回入口 E 确认兑现”规则，必须处于合法返程阶段。
- 实验室内移除/禁用 Hub 购买 UI 快捷入口；可保留旧整备台外观作为装饰，但不能意外绕过跨关卡购买规则。
- 不把现有 `L_Prototype` 直接覆盖删除；做可追溯复制、重命名或过渡别名，保护 Legacy 测试引用。

### 4.3 地图工程要求

- 关卡以 `Content/Maps/` 下明确结构归档（实际文件路径以审计为准），新关卡引用/重定向必须在编辑器重载核对。
- 设置 GameMode、PlayerController、Pawn、HUD、输入映射、NavMesh Bounds、AI 导航、环境灯光、后处理、Audio 正确归属；Lab 与 Hub 使用各自启动位置。
- 使用现有 Blender Python / UE Python 构建生成地图与模型；脚本具备幂等检查，重复执行不得无上限堆 Actor。
- 默认菜单启动 → Hub（而不是直接进 Lab）；提供开发者快捷启动 Lab 的测试路径，但发布 UI 不公开调试快捷键。
- 关键场景人工截图至少：Hub 全景、Hub 商店、Hub 出发门、Lab 入口、A/B/C、Lab 出口、Hub 返回战报。

**验收**：两个独立 Level 均能从新的 UE 编辑器进程重载，独立包可进出，无黑屏、空 Pawn、错误 UI、出生在模型中、从 Hub 可触发追逐等问题。

## 5. T35 — Level 路由、跨局数据与结算幂等（最高技术风险）

### 必做实现

1. 设计一个可测试的 `TransitionService`（只是推荐名）：记录当前阶段、目标关卡、RunId、过渡请求版本，过滤重复请求。
2. 出发时冻结可携装备/扫描资源配置和可选种子；装载 Lab 后初始化一个**全新** RunContext；验证从持久商店购买的效果是否生效。
3. 撤离：先检查合法局内阶段和玩家到达出口、无死亡优先冲突，再以固定 RunId 生成不可变结算，**只更新 SaveGame 一次**。
4. 死亡：不兑现未带出物，生成死亡战报，持久资产不被意外清零；切到 Hub 出生。
5. 技术异常：明确定义是返回 Hub、返回主菜单还是安全错误提示；不得自动认定撤离成功。
6. 实现防止二次点击、重复委托、异步回调迟到、切换场景过程中旧 Timer/AI 访问已卸载世界的保护。
7. SaveGame 版本字段与旧档迁移/兼容策略必须可测试；绝不能将“无法读取旧档”默默替换成零资产新档。

### 关键自动测试矩阵

| 场景 | 必须结果 |
|---|---|
| 新玩家 → Hub → Lab → 撤离 → Hub | 收益仅一次，能再出发 |
| Hub 购买装备 → Lab → 返回 | 装备生效、永久货币正确 |
| Lab 死亡 → Hub | Loot 不兑现，永久升级保留 |
| 同帧 E 撤离 + HP=0 | 死亡优先，只记一条结果 |
| 撤离点连续 E / 回调重复 | 无重复现金、无双重 OpenLevel |
| Lab 退出进程 → 再启动 | 从安全流程恢复，未兑现收益不增加 |
| v0.4 旧存档加载 | 升级/余额迁移或保持，明确结果 |
| 连续 3 次 Hub↔Lab | 无悬挂 AI/音效/Widget/计时器 |

**验收**：状态机日志带 RunId、阶段、触发点、结果、SaveGame 提交次数；不能靠“打开界面看起来没问题”替代。

## 6. T36 — 整备和商店职责迁移

- 仅允许 Hub 调用商店的购买入口；玩家可以在 Hub 查看资源数量、货币、已有升级、装备属性，确认下一局配置。
- 兼容 v0.4 商品及其价格/升级层数/永久属性，不创造另一份商店经济真源。
- 若有局内一次性道具：严格定义购买、携带、消耗、死亡后余量是否返还；优先沿用旧规则，写进 `DECISIONS.md`。
- Lab HUD 只显示局内 HP、扫描、背包、区域信息、异变状态与撤离引导；Hub 不显示追逐 HUD 和实验室倒计时。
- 返回 Hub 的战报显示成功/死亡/异常、入账金额和本局统计；“继续”从战报回 Hub 操作，而非直接重新加载 Lab。
- 验收：主菜单、Hub、Lab、结算 UI 的输入焦点/鼠标显隐正确；在 Hub 按 Q/E/1/2 不意外触发 Lab 开箱、扫描或武器行为。

## 7. T37 — 动态 Lab 箱位（先有限随机，不重造整个地图）

### 设计规则

- A/B/C 每区建立 **至少 3 个合法候选箱位**（最低 9 个点），每轮从各区抽 1 个，仍满足**一轮共三箱、每轮只能开一个、余箱锁定**。
- 使用种子化随机流。固定 Seed + 区域配置 + 回合编号 → 同样的点位与开奖结果随机流契约（若需隔离已有开奖流，独立 BoxPlacement RandomStream，禁止改变旧奖励抽样结果）。
- 生成前校验：地面可站立/不重叠大设备、玩家交互距离及遮挡、可到达 NavMesh、周边怪物导航合法、没有压住撤离出口。
- 与环境事件的占位冲突需检测；如有效候选点不足，使用有限重试 + 固定安全点位，失败时清晰日志，不允许无限循环/无箱死局。
- 提供调试命令或报告输出 `Seed / Round / Region / SpawnPointId / BoxType / EventId`；正式 HUD 不暴露隐藏随机信息。

**验收**：多 Seed 的点位分布检查；连续 20 局可完成可达路径；区域加权收益测试不回归；不同回合不要求每次都换位置，但不应永远固定在同一点。20 局是自动/人工混合的建议测试规模，不能冒充真人样本。

## 8. T38 — 环境互动 I：B 动力区配电系统

**目标**：让“是否断电”成为有利有弊的决策，不只是开关灯。

**最小规格**：
- B 区配置可交互配电箱，E 开/关；显示当前 `POWER ON / OFF` 与中文提示，限定交互距离与遮挡。
- 断电影响 B 区照明、设备音效和一种确切玩法参数，建议 **扫描可靠性下降或扫描时间延长**；另有**正面收益**，建议降低某类设备警报概率或暂时减少观察者可用环境线索。选哪一条必须在审计与调参后记录，不能无成本永远选择断电。
- 配电状态在本局内可切换，离开 Lab 后重置；事件发生时正确处理正在扫描/正在开箱/敌人追逐的边界。
- 环境作用应通过配置与事件接口驱动，而不是散落在 UI、材质脚本、箱代码里的条件判断。

**验收**：开关反馈明确、成本真实影响数字、照明不过暗导致不可玩、扫描结果无非法概率、不会因快速 E 连按重复改写状态。

## 9. T39 — 环境互动 II：C 收容舱

**目标**：让玩家可以主动用环境控制威胁，补充持续跑动之外的操作选择。

**最小规格**：
- C 区存在可识别的收容舱或控制台；在威胁进入指定区域且玩家满足交互条件时，按 E 启动**一次性封锁**。
- 有显式状态 `Idle / Armed / Triggered / CooldownOrSpent`，显示激活条件、失败原因和剩余可用性；避免 UI 告诉玩家能操作但服务端/权威层否决。
- 封锁造成可配置的短暂控制/中断追逐（推荐），而不是无条件击杀怪物或发钱；是否计入现有“成功收容次数”必须按 v0.4 规则审计决定，不能双计。
- 对观察者和普通追逐者明确差异；若无法支持其中之一要显示“该异常无法收容”并在验收中覆盖。
- 关闭或销毁期间清理委托、计时器，确保切回 Hub 不残留。

**验收**：对合法目标可以触发且有反馈，对非法目标拒绝；重复 E、死亡同时触发、脱离场景时没有额外战利品或双重结算。

## 10. T40 — 非掉落动态事件与表现

**至少实现两个可以改变实际决策的事件**，先从以下提案选用，需数据驱动：

| 事件 | 触发条件（示例） | 真实游戏效果 | 反制 |
|---|---|---|---|
| 局部停电 `PowerFluctuation` | 进入 B / 开箱前 | 暂时降低照明并调整扫描参数 | 操作配电设备/等恢复 |
| 收容警报 `ContainmentAlarm` | C 区高风险箱生成或开箱 | 指定短时间威胁加剧、明显警报 | 利用舱/选择先撤离 |
| 样本泄漏（候选） | A 区随机事件 | 暂时限制一处箱位或造成扫描干扰 | 换候选点或消耗装备 |

**规则**：首批采用前两项；单局总事件上限配置化，事件强度随回合缓慢变化，不允许同一秒强行叠加致死组合。固定 Seed 可复现事件 ID、持续时间及影响；要保留非事件局，避免每轮必播造成疲劳。玩家通过声音/灯光/文案能够识别原因与应对。

**验收**：每事件至少含一次正向主流程、边界取消/中断、重复触发保护；不无预警地覆盖箱子随机结果，且保留旧异常分支。

4. **优先复用** v0.4 的 Region、Scanner、Wallet、SaveGame、Shop、Observer、Health 和 Test Harness；不为 v0.5 再造一套并行数据权威服务。
5. **先契约后代码**：涉及金币、物品、装备或回合生命周期的更改必须先更新 `ARCHITECTURE_MAP.md` 与 `DECISIONS.md`，注明旧行为/新行为/兼容策略。
6. **每阶段的闭环**：`PLAN → IMPLEMENT → COMPILE → UNIT/INTEGRATION → VISIBLE TEST → REPORT → CHECKPOINT`，记录测试命令与真实结果；失败不继续加功能。
7. **禁止虚假测试**：不得通过强制成功结果、隐藏关闭关键信号、篡改断言、删除旧测试来制造 PASS；自动测试、人类验收、截图审阅必须分别标注。
8. **禁止破坏资产**：创建新 `.umap` 时不覆盖旧图；生成脚本多次运行保持幂等；生成后的 `.uasset` 必须经过**新进程重载**检查。
9. **资源限制**：遵循历史构建内存经验，不并行暴力编译；大规模生成资产应分批，日志精简，避免上下文爆炸。
10. **回退**：每个 Txx 保存 commit 或完整检查点，更新前后 SHA/变更文件清单；影响 SaveGame 的改动增加迁移/回退实验。
11. **不主动宣称完成真人试玩**；Agent 做不到的音效感受、真实按键及玩法平衡留人工验收单。
12. **阻断报告**：遇到旧版契约冲突、数据破坏风险或地图失效，报告最小安全选项，不推倒重做。

## 15. 最终成功判断

一个没有看过开发过程的玩家能从主菜单进入**安全基地**，理解商店和装备，走进电梯进入一个**独立的危险实验室**；每次前往 A/B/C 能看到不同箱位和环境状态，在电力或收容设备上做有代价的抉择，拿着战利品选择继续或撤离。撤离和死亡都将玩家带回基地，结果正确、存档正确，并且玩家可以继续开始第二局。**这就是 v0.5 的完整可玩纵向切片。**
