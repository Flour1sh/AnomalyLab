# 项目维护规则

更新：2026-09-24。原 v0.1 与用户追加的 T10 均已验收；历史阶段文档已合并清理。

## 阅读顺序与事实来源

1. `Docs/STATE.md`：当前源码状态、人工/自动验收边界、源码与打包版本差异。
2. `Prototype_v0.1_Summary.md`：玩法、架构、交付物和限制。
3. `Docs/01_CONTRACTS.md`：原生/蓝图跨系统接口、执行顺序、关键函数和参数。C++ 迁移现状另见 `Docs/CPP_MIGRATION.md`。
4. `Docs/ASSET_MAP.md`：需要时查询精确资产位置。
5. 打包查 `Scripts/RUN_T09.md`；源模型生成查对应目录的 README_GENERATION.md。

不再依赖已删除的 Ticket、Archive 或中间测试 Markdown。用户明确的新要求优先；
历史脚本、注释和日志不能覆盖当前事实。跨系统需求若与现接口冲突，先说明影响与最小调整。

## 开发边界

- 每次只处理用户授权的范围；新功能先记录范围与验收标准，再实施。
- 保留已验收第一人称移动、观察、跳跃、相机，除非需求明确要求修改。
- 保留职责边界：Interaction 交互、Box 结果、Wallet 金额、Spawner 生命周期、HUD 展示。
- 不因清理或修复擅自加入战斗/HP、联网、存档、背包、检测设备或大型框架；当前玩法核心在 C++，呈现与部分交互在 Blueprint。
- 不改动无关资产或资产包原件；从项目蓝图引用第三方资产。修改现有 uasset 前保留可用备份。
- 旧生成脚本可能覆盖后续修复，重跑前必须检查兼容性，不能依靠脚本编号判断是否安全。

## 实现与验证

- 对象使用前 IsValid；一次性行为和委托防重复；清理计时器、绑定和过期 Actor 引用。
- 蓝图图保持清晰、命名明确；编译和保存每个修改的资产，必要时独立重载复核。
- 只做与修改相关的回归。玩法、实体输入与视觉不能由结构检查代替；独立包也不能仅用 PIE 代替验收。
- 区分自动通过、用户总体确认和未执行项，不能补造样本数、运行日志或逐项结论。
- 测试后恢复随机模式及正常类引用，不保存故障注入或强制结果到生产默认值。
- 日志只提取相关类别和时间范围；不要倾倒整个 Content、复杂蓝图或全部 Output Log。
- 遵守用户当前对 Python、MCP、PIE 和屏幕操作的限制，不擅自切换操作方式。

## 文档与交付

- 功能变更后同步 STATE、接口与必要路径；STATE 尽量不超过 100 行，写当前事实而非开发日记。
- 总结是总体入口；技术细节集中在接口文档，避免重新积累每阶段重复文档。
- 明确修改资产、验证结果、限制及交付目录；区分当前源码和已打包版本。
- 原始日志、JSON、备份、脚本与构建产物不随 Markdown 清理删除。
